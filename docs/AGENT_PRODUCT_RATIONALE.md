# Why these capabilities belong in an agent product

Date: 14 October 2026. This is an explanation of the approved Lotuspond direction and a proposed prioritization lens, not a change to the requirement register, an implementation claim, or a new screen specification. Existing work and goals remain preserved. Automation Anywhere is a category reference; it does not determine Lotuspond's navigation, data model, or feature acceptance.

Lotuspond's core customer promise is to help people build agents that use permitted information and tools to achieve a defined outcome, then understand, improve and control those agents in operation. The need for supporting modules follows from what the agent is allowed to do and how long its work lasts. A read-only assistant needs fewer operational capabilities than an agent that changes an order, waits for approval and resumes tomorrow. Sophistication means handling the chosen customer's real constraints coherently; it does not mean exposing every backend component as a product module.

## A concrete reference journey

Consider an order-request agent. A customer submits an incomplete request. The agent interprets it, retrieves the permitted product and account context, asks for missing information, checks available tools, and proposes an order. A reviewer sees the exact proposed change when approval is required. The permitted connector submits it, the system reads back the result, and the customer sees the order reference or an explicit unresolved exception. If a model is unavailable or a worker restarts, the request is retained. If submission times out, the system reconciles it before attempting another order.

This is an illustrative example drawn from the existing reference-pack options, not a decision that order processing is the first market. For a knowledge assistant, the success criteria could instead be a supported answer with citations and appropriate abstention; an external business write and its approval would not be invented merely to use the platform.

## Capabilities, customer needs and UI boundaries

| Capability | Concrete customer need | What needs visible UI | What can remain infrastructure; first-workflow boundary |
| --- | --- | --- | --- |
| Agent definition and bounded reasoning/tool loop | “Understand this request and complete the permitted task, within a budget.” | Goal, instructions, input/output expectations, model, permitted tools, context, stopping/escalation rules and test results. | Typed definitions, execution limits and tool routing. Core to the first agent. Multiple collaborating agents are conditional, not a prerequisite. |
| Studio | “I can configure, test and improve my agent without editing deployment machinery.” | An agent workspace organized around behavior and evidence: configuration, test conversations/cases, traces and version comparison. | Shared SDK/compiler and validation. A constrained editor serves the first supported workflow; a broad canvas or large node palette is not the starting experience. |
| Models and tools/connections | “Use the right model and business system without exposing credentials or allowing arbitrary actions.” | Model choice within allowed options, tool purpose/input/output, connection setup, permissions and clear failures. | Credential resolution, tenant checks, destination restrictions, rate limits and connector adapters. Begin with the actual required model and connectors. |
| Knowledge, context and artifacts | “Use our current, authorized information and show where the answer came from.” | Source selection, retrieval preview/citations, freshness/access problems and retention controls where users make decisions. | ACL filtering, ingestion, immutable source references, bounded context and artifact storage. Use the first workflow's sources; a general ingestion marketplace or vector-database management UI is not required. Conversation memory also needs explicit scope and retention. |
| Evaluations and assurance | “Show that a prompt, model or tool change improves behavior without causing regressions.” | Representative cases, quality/cost/latency results, comparisons, release decisions and evidence. | Evaluation execution and scoring pipelines. Reuse existing Scenarios, Releases, Production Evidence and Governance. A minimum representative regression set is essential; full benchmark catalogs are later breadth. |
| Debugging and observability | “Why did this request fail, select that tool, or become expensive?” | Inspectable inputs, context/citations, tool arguments/results, checks, errors, timing and cost, subject to permissions/redaction. | Correlated traces, metrics, durable history and retention. Do not promise access to a model's private chain of thought. First workflow needs an understandable trace and actionable errors. |
| Durable execution | “Do not lose my request when a process crashes or a person replies tomorrow.” | Progress, waiting reason, cancellation limits and clear recovery status. | Checkpoints, timers, retries, deduplication, outbox/inbox, version pinning and recovery fencing. Essential for asynchronous or consequential work; it does not need its own customer administration console. |
| Queues and capacity | “Handle a burst fairly, respect provider limits, and tell me when my work is delayed.” | Usually a status, backlog/age signal and actionable exception within operations. A business worklist is visible when people must claim/prioritize requests. | Dispatch queues, backpressure, fairness and concurrency are internal. A separate queue-management screen is justified by actual routing/SLA/assignment needs, not by the presence of a queue implementation. |
| Human oversight | “Let me approve a consequential change, supply missing information, or take over.” | An actionable task/inbox or contextual review showing proposed action, evidence, uncertainty, expiry and consequences; approve/reject/edit-and-repropose as allowed. | Durable waits, assignment, exact-action binding, reauthorization and audit. Include the oversight the first workflow requires; not every read-only tool call needs approval. |
| Actions, cases and verified outcomes | “Was the order actually created, and who owns the unresolved request?” | A customer request/case timeline, final outcome, evidence and exception owner. | Distinct action attempts, receipts, read-back, reconciliation and compensation contracts. Essential when the agent changes external state. An evaluation Run remains distinct from a business Execution. |
| Control Room / operations | “See which agents are healthy, what is waiting or failing, what it costs, and where intervention is needed.” | One focused operations workspace: deployments, executions/outcomes, waiting tasks and actionable incidents. Different roles can see different entry points. | Scheduling, recovery coordination and telemetry aggregation. First workflow needs operational visibility and intervention, not a mandatory collection of fleet/queue/environment dashboards. Studio and Control Room are capabilities within one product. |
| Versions, registry and deployment | “Test a change, know what is running, and retain reproducibility for work already in progress.” | Named versions, meaningful diffs, evaluation evidence, deployment selection and clear rollback/new-work behavior. | Immutable packages, hashes, signature/trust checks and pinned configuration. Foundation for the first deployed workflow; hashes/compiler terminology need not dominate the builder journey. |
| Triggers and schedules | “Start when a request arrives, or at the time our business needs.” | Configuration and failure/next-occurrence visibility for the selected trigger. | Authentication, replay/deduplication and persisted timing. One appropriate start mechanism suffices initially; a schedule builder is needed only for a scheduled use case. |
| Runtime identity, workers and fleet | “Run near our data and stop a revoked worker from acting.” | Setup/connection health and revocation controls for the responsible administrator; detailed fleet views only when multiple sites/pools need operation. | Worker identity, isolation, enrollment, routing, capability matching and revocation. Secure execution identity is essential; broad fleet orchestration depends on topology and scale. |
| Identity, governance and administration | “Only the right people and agents can access data, deploy changes or approve actions.” | Minimal member/role, connection permission, policy, audit and retention controls relevant to the customer. | Tenant isolation and enforcement at every action/data boundary. Essential from the first shared customer deployment. Federation, provisioning, delegated partners and advanced enterprise controls depend on the buyer; some buyers need them immediately. |
| Usage and licensing | “Understand costs, limits and what happens when capacity or entitlement expires.” | Spend/usage/limits and understandable entitlement status; simple administration initially. | Budget enforcement and auditable usage/entitlements for the licensed offering. Cost control is an agent need; commercial licensing supports the business model. Automated billing, complex editions and partner commerce are later unless explicitly required. |
| Packs, reuse and improvement | “Start from a proven task and turn failures into regression tests.” | Supported templates, configuration, representative examples and reviewed improvement suggestions. | Versioned connectors/evaluations/policies, authorized incident-to-test conversion and provenance. One qualified reference pack comes first; broad marketplaces and industry catalogs are expansion. |
| Installation, security and operations engineering | “Install, update, recover and support the product without losing work or data.” | Health, actionable setup/upgrade errors, export/recovery guidance and support paths. | Artifact integrity, migrations, backups, telemetry, alerting, load/failure tests and runbooks. Baseline qualification is essential for the chosen first topology; qualifying every topology is separate work. |
| Voice, browser/desktop, legacy systems and partner access | “Reach the actual channel or system this task depends on.” | Appropriate conversation/handoff or device/session controls only for supported use cases. | Channel adapters, isolation, credential handling and lifecycle protocols. Existing work stays preserved; first-workflow inclusion depends on the selected channel/system, not feature parity. |

## Studio should start with the agent

The primary object should be an agent's intended behavior and evidence of its performance. A proposed first authoring sequence is:

1. **Goal and success:** task, intended users, input/output contract, examples of success/failure and when to ask a person or stop.
2. **Instructions and behavior:** system instructions, constraints, allowed autonomy, uncertainty/abstention and handoff rules. Instructions and retrieved content never grant permissions.
3. **Model:** approved model/configuration, structured-output requirements, context/token/cost limits and any explicitly supported fallback policy.
4. **Tools:** purpose and typed inputs/outputs, read versus write effects, connection permissions, approval requirements and safe test facilities.
5. **Knowledge and context:** authorized sources, retrieval strategy, citations/freshness, supplied task context and scoped conversation memory. Avoid adding a new storage product unless the workflow needs it.
6. **Evaluate and debug:** run representative cases beside the configuration, inspect context and tool interactions, compare versions, and surface quality, latency and cost tradeoffs. Test uncertain results, misuse attempts, denied actions and provider failures.
7. **Human oversight and deployment:** preview exactly what reviewers will see, define escalation/ownership, review changes and publish an immutable version into an authorized environment.

The graph is a useful secondary view when branches, waits, parallelism or a sequence of independently controlled actions need explanation. A simple agent should not require customers to manually draw orchestration infrastructure. AI-assisted authoring can propose goals, instructions, tool mappings and tests, but its draft remains reviewable and cannot silently broaden permissions or publish.

This is a rationale for subsequent UX design, not a replacement of the approved shared SDK/compiler contract or a claim that Studio is implemented. The SDK remains a full authoring path for engineering users; the UI writes the same definitions and uses the same validation.

## First complete workflow versus enterprise expansion

For the illustrative action-taking workflow, the first complete slice needs one defined customer outcome, one supported model, the necessary authorized context/tools, bounded agent behavior, a usable configuration/test experience, representative evaluations, versioned deployment, one input mechanism, durable request/action state, the required human intervention, exact write controls/read-back, clear outcomes/exceptions, useful traces and cost limits. It also needs tenant/identity boundaries, a qualified installation/upgrade/recovery path, and an identified operator. A successful demo alone does not establish customer production readiness.

The first operations UI can be an execution/outcome list, a detail timeline and actionable human tasks, with deployment and connection setup. Queues, the engine, workers and retry machinery can largely remain underneath those views. Baseline accessibility and privacy are first-customer requirements, not later polish.

A broader visual designer, multi-agent coordination, advanced business queue administration, many worker pools, rich schedule calendars, large connector/knowledge catalogs, organization-wide analytics, multi-region/air-gap variants, federation/provisioning, delegated partners, marketplace distribution and automated commercial operations are expansion candidates. They remain in the approved requirement register. “Later” is sequencing, not removal: a first buyer's topology, security procurement or actual workflow can move any of these onto the critical path. In particular, essential access controls, durable recovery and required action approvals are not postponed as enterprise extras.

## Assumptions requiring owner clarification before scope changes

| Current working assumption / open choice | Why clarification matters |
| --- | --- |
| The first task is a bounded operational workflow; order/document intake is only an example. | A research/knowledge assistant, support agent, transaction agent or voice agent has a different minimum tool, state, outcome and oversight surface. Identify the buyer, actual systems and measurable accepted outcome. |
| The first builder is an AI/application engineer or technically supported process owner. | A business-only builder may need a stronger guided authoring experience immediately; an engineering-first customer may prefer SDK configuration with test/debug UI. This changes UX priority, not the need for a shared contract. |
| The agent may propose consequential actions, with approval where the customer's policy requires it. | Clarify permitted autonomy, prohibited actions, required reviewers and acceptable exceptions before selecting default approval flows. Neither universal approval nor unrestricted autonomy is assumed. |
| The initial deployment follows the approved connected, isolated installation with Linux workers. | Hosted-only, customer-network access, BYOC or offline needs change identity, deployment, fleet and operational requirements. No infrastructure or customer access is authorized by this assumption. |
| The first workflow has a limited set of authorized knowledge sources and a defined retention policy. | Clarify data types, jurisdictions, ACL sources, model egress, memory needs and deletion expectations before expanding ingestion or storage. |
| Workload and waiting/SLA needs are not yet buyer-validated. | Volume, duration, parallelism, business priorities and human wait times determine whether customers need a business queue UI, extra capacity controls or more deployment complexity. Roadmap load targets remain hypotheses. E04's local load calibration (2026-10-27) measured an installation-wide serialization limit well below the planning target, so the buyer's real volume should decide how much engine capacity work comes next. |
| We have not fixed which enterprise requirements are purchase blockers for the first customer. | SSO/provisioning, audit export, private models, local hosting, support hours and partner access may be day-one requirements for a particular buyer. Commercial terms and acceptance ownership also need explicit agreement. |
| Studio and Control Room name capabilities; their exact navigation and screen boundaries are still a UX decision. | Confirm the preferred user vocabulary through the selected users/journey before locking screen structure. Automation Anywhere labels should not create screens by themselves. |

These questions do not block current pure SDK/contract work. No requirement is being dropped, renamed out of existence or silently deferred by this memo. Any proposed change to approved scope or acceptance criteria should identify the affected requirement, customer evidence, tradeoff and preservation/migration impact first.
