# Lotuspond API and workers

The API root is `/api/v1`. JSON errors contain `error` and `message`; validation errors list field paths without echoing submitted secrets. Mutations require `application/json`. The normal request limit is 2 MiB. Readiness is `/ready`; `/health` only reports process liveness. `/changelog` returns the console's `items` collection.

## Authentication and ownership

`POST /auth/register` accepts `{email,name,password,account_type,workspace?,invitation_token?}`. Public registration defaults to disabled; enable it explicitly for open signup. An active matching invitation allows individual signup on a closed installation, but it does not accept the invitation or grant organization membership. `account_type` defaults to `individual`; `organization` requires `workspace`. Every account gets a personal workspace. Development organization signup creates a separate organization and returns its `workspaceId`. Production requires individual signup and mailbox verification before explicit organization creation; an organization signup request returns `identity_unverified`. `POST /organizations {name}` adds an organization later. `GET /me` returns the user, including `email_verified`, their workspaces/roles, and `capabilities` booleans for `mail_enabled` and `registration_enabled`.

`GET /me` also includes `user.identity_verified`, `user.identity_verification_source` (`mailbox`, `operator_attested`, or null), and `capabilities.offline_enrollment_enabled`. These identity fields do not replace `email_verified`. Production organization creation may also use a completed, active offline operator attestation.

`POST /auth/login` and `/auth/logout` manage HttpOnly, SameSite=Strict sessions. Mutating browser requests require the configured Origin; production cookies are Secure. Workspace requests carry `x-lotuspond-workspace`. Read-only members cannot mutate data. Pending offline accounts cannot use password login, sessions, or attributed API keys.

`GET /auth/sessions` lists the signed-in user's active sessions with `id`, `created_at`, `expires_at`, and `current`; no session token or hash is returned. `DELETE /auth/sessions/:id` with an empty JSON body revokes an owned session and returns `{ok,signed_out}`. Other accounts' identifiers return 404. A user can keep at most 20 active sessions; a new sign-in prunes expired sessions and the oldest excess sessions.

`POST /auth/password` accepts `{current_password,new_password}`. The new password must have 12–256 characters and differ from the current password. This operation verifies the current password, revokes every existing browser session, and issues a fresh cookie to the current browser atomically. Account events are audited in the personal workspace. Concurrent sign-in checks lock the account so an old password cannot create a session after the password change commits. Password changes invalidate pending recovery challenges. Forgotten-password recovery uses the separate email challenge flow below.

Headless integrations use `Authorization: Bearer <key>`. Its embedded workspace ownership overrides any client workspace header. Available scopes are `read`, `write`, `run`, `ingest`, and `gateway`. Human administrator sessions are required to add members, manage keys, create governance policies, or decide approvals. Production organization access and operator actions require verified mailbox ownership or an active operator attestation linked to completed offline enrollment. Organization API keys also require an attributed, active, verified creator. Existing unattributed keys require deliberate replacement by a verified administrator; migration never guesses an owner.

## Authenticator MFA

For an account with an enabled authenticator, `POST /auth/login {email,password}` returns HTTP 202 `{mfa_required:true,challenge_token,expires_at}` and creates no authenticated session. Keep the challenge in memory. Complete it using `POST /auth/mfa/challenge/complete {challenge_token,code}` with the current six-digit TOTP or an unused recovery code. Successful completion returns `{ok:true}` and an HttpOnly session cookie. Challenges expire after five minutes and allow at most eight failed code attempts, in addition to account/IP rate limits. Repeating a consumed challenge or code fails.

`GET /me` includes `mfa: {available,enabled,session_verified,recovery_codes_remaining,required_for_privileged,required_by_installation}`. `required_by_installation` reports the operator's installation-wide requirement, which covers personal workspaces as well and cannot be changed through the API. These fields are distinct from mailbox/attested identity verification. `required_for_privileged` applies to production platform operators; `/admin/*` enforces verified identity, operator role, configured MFA, and a session bound to the current factor. API keys cannot access platform administration.

| Method/path                                | Contract                                                                                                                                                                  |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST `/auth/mfa/enrollment/start`          | Session and `{current_password}` required; rotates sessions and returns `{secret,otpauth_uri,expires_at}` for provisional setup. An enabled factor cannot be overwritten. |
| POST `/auth/mfa/enrollment/confirm`        | Session and `{code}` required; consumes a valid pending setup, enables MFA, rotates sessions and returns `{ok,recovery_codes,message}` once.                              |
| POST `/auth/mfa/recovery-codes/regenerate` | Session and `{current_password,code}` required; verifies a fresh factor/recovery code, replaces all codes and sessions, returns new recovery codes once.                  |
| POST `/auth/mfa/disable`                   | Session and `{current_password,code}` required; removes the factor and recovery material and rotates sessions. Production platform operators receive 403.                 |

### Organization authenticator policy

An organization can require an authenticator for everyone who reaches it. `GET /settings` returns `authenticator_policy: {require_mfa,available,manageable}`, plus `members_without_authenticator` for workspace administrators, and the workspace record itself carries `require_mfa`. `POST /settings/authenticator-policy {require_mfa}` returns `{ok,require_mfa,members_without_authenticator}`.

Only an owner or administrator who already holds an enabled factor can change the policy, so it cannot lock out its author. A personal workspace returns `policy_unavailable`; an installation without the authenticator encryption key returns `mfa_unavailable`. An installation-wide requirement (`LOTUSPOND_REQUIRE_MFA`) applies the same rule to every workspace, including personal ones, and takes precedence in the refusal message. While either requirement is on, a member or API-key creator without an enabled factor receives 403 `mfa_required` for the workspaces it covers; their personal workspace, account pages and enrollment stay reachable. Withdrawing the policy restores the previous access immediately. Disabling your own factor while an organization requires one removes your access to it, including this endpoint, until you enroll again. The policy applies to human authority and inherited key authority, not to the separate production verified-identity gate, which continues to apply on its own.

### Account change notices

When mail is configured, a password change, a completed password reset, an authenticator enrolment, an authenticator removal and a recovery-code reissue each queue one `security_notice` message to the account mailbox. It names the change and the time it was recorded and deliberately carries no link, token or code, so it cannot be turned into a phishing lure and needs no expiry. It references no challenge or invitation, so the worker never cancels it as stale. A disabled or unconfigured mailbox queues nothing and never blocks the security change; the API response is identical either way and never reports delivery.

### Assisted authenticator reset

Losing both the authenticator and every recovery code has no self-service path, so an organization owner or administrator can clear it for a member: `POST /auth/mfa/members/:id/reset {current_password,reason}`. It must be a different person (`different_administrator_required`), requires the acting administrator's own password, works only inside an organization (`organization_required`), and refuses a platform operator's factor so a workspace cannot clear what protects the installation. It only removes — the factor, recovery codes, pending enrolment, sessions and login challenges — and issues no session, factor or password, so it cannot be used to take over the account. The member is notified out of band and enrols again with their own password. The change is audited with the reason.

Only factor-management responses disclose setup/recovery material, and all API responses carry `Cache-Control: no-store`. No token, code, secret or ciphertext appears in account state or audit details. Password changes preserve the current session's legitimate MFA binding; password reset revokes sessions/challenges but leaves MFA enabled. Configure the separate encryption key and follow the [MFA runbook](../docs-site/docs/mfa.md). Losing all second-factor material has no self-service reset.

## Verification, recovery, and invitations

| Method/path                         | Contract                                                                                                                                            |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST `/auth/verification/request`   | Session required; `{}` queues a verification challenge and returns 202 `{status:"accepted"}`. Mail unavailable returns 503.                         |
| POST `/auth/verification/confirm`   | `{token}` consumes the expiring verification challenge once; returns `{ok:true}`.                                                                   |
| POST `/auth/password/reset/request` | `{email}` returns the same 202 `{status:"accepted"}` for eligible and unknown accounts, including when mail is disabled.                            |
| POST `/auth/password/reset/confirm` | `{token,new_password}` consumes the recovery challenge, changes the password, revokes sessions, and returns `{ok:true}` without signing in.         |

| POST `/invitations`                 | `{email,role,days?}` creates an invitation and encrypted queued mail; roles `admin`, `editor`, `viewer`; 1–30 days, default 7.                      |

Verification and reset challenges expire after 30 minutes. Requests are rate limited; reissuance invalidates older pending challenges of the same kind. Invitation creation does not alter membership, and acceptance does not change an existing member's role. Expired, used, revoked, mismatched, or suspended-organization invitations fail closed.

The mail worker is `npm run worker:mail`, or `python -m lotuspond.mail_worker`. See [identity mail](../docs-site/docs/identity-mail.md) for the protected configuration and opt-in Compose profile. A 202 response means only that the request was accepted; it does not prove SMTP submission or inbox delivery. Outbox ciphertext and token hashes are omitted from API and audit output.

## Offline enrollment

In airgap mode with mail disabled, `POST /auth/offline-enrollment/inspect {token}` returns the provisioned name/email, expiry, optional organization, projects, and identity source. It excludes the operator's check references. `POST /auth/offline-enrollment/complete {token,password}` consumes a valid pending link once and establishes the password. It issues no session cookie; sign in normally afterward. Both endpoints enforce rate limits and browser origin checks. Expired, consumed, revoked, suspended or unauthorized enrollments fail closed.

Provisioning and pending-link reissue are privileged CLI operations, not public registration endpoints. See [offline enrollment](../docs-site/docs/offline-identity.md) for explicit organization/admin selection, private token delivery, and limitations. Operator attestation never sets `email_verified` and cannot accept an email invitation by itself.

## Trace costs

`POST /traces` accepts nullable/omitted `cost_usd`, bounded to 0–1,000,000 USD with at most six decimal places. The server sets `cost_measurement`: a supplied value including zero is `reported`; omitted/null is `unavailable`. Clients cannot choose the marker. Existing amounts retained through schema upgrades are `unknown`. Idempotency compares both amount and measurement provenance; retrying a historical unknown value as reported returns 409 instead of rewriting evidence.

OTLP ingestion recognizes the exact span attribute `lotuspond.cost_usd` with the same numeric limits. Missing attributes leave cost unavailable. Invalid supplied values reject that span. `GET /overview` returns `monthly_cost_usd`, a nullable subtotal of reported current-month trace costs, plus `monthly_cost_counts: {reported,unavailable,unknown}`. No reported traces means a null subtotal. Nonzero unavailable/unknown counts mean incomplete measurement coverage. Producer-reported costs are not the authoritative gateway ledger or reconciled billing.

States are `fresh`, `stale`, `missing`, `disabled`, `not_configured`, or `unavailable`. The response contains aggregate numbers, not tenant identifiers or evidence. A database failure returns a sanitized 503; Redis failure leaves queue measurements available and marks observations unavailable. `/telemetry/otlp` accepts an identity or `gzip` encoded body and refuses any other with 415 `unsupported_encoding`. A gzip body must be a single member; the decompressed form is bounded by the same `max_request_bytes` budget as the wire body and exceeding it returns 413 `body_too_large`, so a small highly compressible payload cannot expand past the limit. It is the only mutating route that accepts a media type other than `application/json`: `application/x-protobuf`, the OpenTelemetry SDK default, which a cross-site form cannot submit any more than it can submit JSON. A protobuf `ExportTraceServiceRequest` is decoded (`backend/lotuspond/otlp_protobuf.py`) into the canonical OTLP/JSON form — hex identifiers, integer enums, 64-bit integers as decimal strings, bytes as base64, default-valued scalars left out — and then meets the same validation, allowance and redaction as JSON, so both encodings store identical traces. Unknown fields are skipped; a known field with the wrong wire type, a length past the end, a non-UTF-8 string or attribute values nested more than 32 deep return 400 `invalid_body`, as does a JSON body that is not an object. A protobuf export is answered 200 with an `ExportTraceServiceResponse` (`application/x-protobuf`): empty when every span was kept, otherwise `partial_success` with the number of spans not stored and why. Errors stay JSON for both encodings. The audit record `telemetry.otlp_ingested` names the encoding.

## Subscription levels

A workspace holds one of three tiers: `developer`, `team` or `enterprise`. The ladder is a static server definition, so a request body can never name a fourth, and a database constraint keeps the column inside it. Only a platform operator can change a workspace's tier, through `PATCH /admin/workspaces/:id/plan` with a reason that is audited; a workspace administrator cannot upgrade their own workspace, because Lotuspond collects no payment and an upgrade is a commercial act an operator performs elsewhere.

`GET /settings` returns `billing: {plan, entitlements:{monthly_trace_quota,trace_retention_days}, usage:{traces_this_month,traces_remaining}, payment}`. `payment.status` is always `not_collected`: no payment instrument is stored and nothing is charged.

The tier decides two things about traces. The **monthly allowance** is enforced when a trace is stored: `POST /traces` returns 402 `trace_quota_exceeded` once it is spent, and `/telemetry/otlp` reports `quota_rejected_spans` separately from `rejected_spans` so a producer can tell a quota wall from malformed data, returning 402 only when nothing at all was stored. Usage counts server receipt time, so a backdated `occurred_at` cannot be ingested outside the month it arrived, and an idempotent replay stores nothing and therefore spends nothing.

The **retention window** decides how long Lotuspond promises to keep a trace. It governs deletion, not visibility: a trace stays readable and exportable until the separate `npm run retention` job removes it, so changing a plan never makes evidence silently disappear. That job reports by default, deletes only with `--apply`, refuses a run above `--max-deletions`, and writes an audit record per workspace naming the plan and cutoff. `GET /traces/export` is available on every plan and returns canonical JSON with its own `export_sha256`; a subscription decides how much evidence is accepted and kept, never whether a customer may take their own evidence with them.

Core workflow lists accept `limit` (1–100), `before`, `before_id`; responses include `items` and `next`. Project-aware lists accept `project_id`. Monitoring lists currently return bounded/current collections rather than the full core cursor contract. Read the generated OpenAPI schema at `/openapi.json` and `backend/lotuspond/schemas.py` for exact input bounds. Policy rates accept up to four decimal places; monetary limits accept up to six, preventing silent database rounding from weakening a gate.

## Execution worker

Set `LOTUSPOND_API_URL` (default `http://127.0.0.1:8000/api/v1`), `LOTUSPOND_API_KEY`, and `LOTUSPOND_RUNNER_ID`:

```sh
npm run runner -- /absolute/path/to/adapter.mjs
```

The local adapter exports `async evaluate(input, expected, {revision,signal})`. It executes the real workload and returns `{passed:boolean|null,output:object,costUsd?:number,evidence?:object}`. Honor cancellation. Unknown evidence must remain null; every run result is required. The adapter executes in a customer-controlled process, not inside the API. Use a configured isolated sandbox for untrusted code.

Infrastructure errors and timeouts are unknown outcomes. Omitted cost, or explicit `evidence.cost_measurement="unavailable"`, is not measured zero: aggregate cost is null and a configured maximum-cost policy blocks. Explicitly supplied finite nonnegative cost, including zero, is treated as producer-reported. The MCP adapter marks cost unavailable because the protocol does not supply a billing measurement. Its independent package supports an operator-selected Streamable HTTP endpoint/tool and exact `contains` or `equals` expectations; truncated or unsupported output remains unknown. See `protocol-adapters/README.md` for setup and its local-test evidence boundary.

## Semantic worker and provider configuration

`npm run worker` claims durable assessment jobs. Traces with enabled project monitors enqueue according to deterministic sampling. Manual assessments are also queued. The worker retains input digests, transcript revision identifiers, provider/model, and reasons; expired leases cannot submit stale results.

Configure `LOTUSPOND_TYPESAFE_BASE_URL`, `LOTUSPOND_TYPESAFE_API_KEY`, `LOTUSPOND_TYPESAFE_MODEL`, and optional timeout for Jev. Missing configuration, invalid evidence, provider failure, or disabled cloud access produces unknown. Semantic findings do not authorize tools or override deterministic governance.

The chat gateway uses `LOTUSPOND_PROVIDER_URL`, `LOTUSPOND_PROVIDER_KEY`, and `LOTUSPOND_PROVIDER_MODELS`, a JSON array of `{id,input_usd_per_million,output_usd_per_million}` with operator-verified prices. Requests reserve budget before network activity, and the independent ledger retains settled or uncertain usage. Provider URLs require HTTPS and cannot carry embedded credentials; redirects and ambient proxies are disabled. Streaming remains unimplemented. No provider is configured by default.

## Incident review and alerts

`GET /incidents` accepts `status` (`open` or `resolved`), `category` (`manual`, `assessment_failed`, or `assessment_unavailable`), `project_id`, and the core `limit`/`before`/`before_id` cursor. `GET /incidents/:id` returns `{incident,project,trace,voice_session,assessment,monitor,history,alerts}` with nullable linked records. Alert payloads, endpoint URLs, signing secrets and lease hashes are excluded.

`POST /incidents/:id/resolve` accepts an optional `{reason}`; an omitted reason retains compatibility with existing clients. `POST /incidents/:id/reopen` requires `{reason}`. State changes require write authority, append history and audit records, and enqueue configured operator alerts atomically. Repeating the same state is idempotent. Failed assessments open failure incidents; unknown assessments open evaluation-unavailable incidents and never claim that the agent failed.

Optional `npm run worker:alerts` delivers signed, bounded metadata to operator-configured HTTPS destinations. Configuration is shared with the API and evaluation worker; the default destination list is empty. See [incidents and alerts](../docs-site/docs/incidents.md). A delivered record proves HTTP 2xx acceptance only.

New run creation rejects larger frozen snapshots with HTTP 413 and `run_snapshot_too_large` before creating a run or audit record. Capability matching occurs before claim row locking; all frozen scenario modalities must be supported, missing modality defaults to text, and an empty runner capability list remains unrestricted. Leases last 15 minutes and renewal resets expiry to 15 minutes from server time. Customer-side clients accept `LOTUSPOND_API_URL` as an origin or as the `/api/v1` base. See [runner execution](../docs-site/docs/runners.md) for subprocess deadlines, cancellation, packaged commands and credential handling.

## Immutable workflow package registry

Publication stores a fully validated declaration; it does not install, approve, trust or execute it. The complete semantic validator checks graphs and references as well as the strict v1 schema. Private manifest text remains workspace data. Secret references remain identifiers and are never resolved here.

| Method/path | Contract |
| --- | --- |
| POST `/projects/:project_id/packages` | Raw v1 manifest JSON, `write` authority, optional `Idempotency-Key`. Returns publication metadata: 201 new version, 200 identical canonical replay, 409 conflicting immutable version or request key. |
| GET `/packages?project_id=...` | `read` authority, metadata only, `limit` 1–100 (default 50), optional opaque `cursor` up to 1024 characters. Returns `{items,next}`; pass `next` as the next request's cursor. |
| GET `/packages/:id` | Scoped publication metadata. |
| GET `/packages/:id/content` | Exact stored canonical JSON bytes with `X-Package-SHA256`, `X-Package-Canonicalization` and quoted digest `ETag`; no revalidation or rewriting on read. |
| GET `/package-contracts` | `read` authority; supported admission schema, validator revision, canonicalization identifier and package byte bound. No runtime compatibility claim. |

Workspace membership controls projects; there is no additional project ACL in this slice. Owner/admin/editor can publish, viewer can read. API-key scopes are exact: a `write` key has no implicit `read`. Key ownership overrides the workspace header. Foreign-tenant projects and versions return the normal 404; platform operators have no bypass. Current suspension, expiry/revocation, active creator, verified identity and MFA gates remain applicable on every request.

Send exactly `application/json` (optional charset parameter) with identity encoding and the existing permitted Origin for browser requests. A package is bounded to 1 MiB while reading regardless of Content-Length. The shared CLI/API decoder rejects duplicate keys, malformed UTF-8/JSON, nonfinite or oversized numbers, excessive nesting and invalid Unicode; the full validator rejects extra fields, unsupported schemas and invalid graphs/references. Errors carry safe codes and fixed paths/messages without submitted values.

A publication's identity is `(workspace_id, project_id, package_id, version)`. Identical canonical bytes reuse the original version and admission metadata, including when no request key is supplied. Different canonical bytes cannot overwrite it. Array order remains meaningful; JSON key order and formatting do not. Request keys are optional, preserved exactly, 1–128 visible ASCII characters without spaces, and unique within a workspace. The normalized request hash uses SHA-256 over the fixed `lotuspond.package-publication.v1` context, NUL, normalized project UUID, NUL and canonical content. Reuse with another payload or project returns 409. Keys have no expiry in this increment; choose a fresh key for a new request.

Database uniqueness and one outer transaction cover version, key and audit. Concurrent identical publication emits one publication audit event; conflicting key races roll back any candidate version. Successful replays emit no second publication audit. No update/delete endpoint exists. No global cross-workspace content deduplication exists.

Metadata includes server `id`, UTC `created_at`, authenticated `workspace_id`, `project_id`, logical `package_id`, `version`, `schema_version`, `validator_revision`, `canonicalization`, `sha256`, `content_bytes`, `publisher_id` and `publisher_kind` (`user` or `api_key`). Names, instructions, manifest objects and request keys are excluded from metadata/list/audit responses. Audit details contain project/package/version/digest identifiers only.

Current admission identifiers are `lotuspond.workflow-package.validator.v1.1` and `lotuspond.workflow-package.canonical-json.v1`. The canonicalizer uses fully validated values with defaults, sorted object keys, UTF-8, compact JSON separators, finite numbers and preserved array order. These names permanently describe the stored content's admission, not execution compatibility. Future validator revisions must use a new server identifier and preserve existing stored bytes/identifiers.

Pagination orders by descending `(created_at,id)`, so equal timestamps retain stable identity ordering. Cursors bind workspace and project; they confer no authority. New publications do not change the older rows reached by an existing cursor.
