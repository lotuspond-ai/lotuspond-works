# Connections and runtime identity foundation (E03)

Date: 14 October 2026 (Asia/Kolkata). Status: proposed written specification for owner review under the approved product completion sequence. Implementation planning and implementation have not been approved for this specification. The existing choice of subagent execution with independent review remains recorded; it does not bypass written-spec or plan review.

## Intent and preserved scope

A customer needs an agent to use the right business systems under explicit permissions, keep credentials near execution, and stop accepting new work when its worker is revoked or loses current authority. E03 establishes that identity and connection foundation for the approved first topology: one connected, isolated customer installation and Linux runtime pool. It preserves the full [completion design](2026-10-14-product-completion-design.md), [agent product rationale](../../AGENT_PRODUCT_RATIONALE.md) and all remaining workflow, UI, licensing, enterprise and deployment goals.

Studio will select permitted tools and connections; operations will show connection/worker health and actionable failures. E03 does not prescribe additional screens or an Automation Anywhere navigation model. Its administration API and local bootstrap tooling precede the later integrated Studio/Control Room experience.

The accepted engine probe supports Temporal as the preferred candidate for later durable orchestration, with [findings and limitations recorded separately](../../plans/2026-10-14-durable-engine-probe.md). E03 installs no engine dependency. Customer identity, connection policy, replay protection and recovery authority remain independent of an engine's restored history.

## Architecture and alternatives

Recommended: extend the existing Python API/PostgreSQL authority with scoped connection and fleet records; add an independently installable Python runtime client with outbound verified HTTPS, separate opaque machine credentials, existing SDK command signatures, durable replay checks and worker-local secret resolution. Keep the pure SDK free of API/database/network dependencies. Existing human/API-key authentication, evaluation runners, evaluation `Run`, v1 registry bytes and executable-v2 wire/signature contracts remain intact.

Standard mTLS or workload identity is a supported future integration boundary and can become first-customer work if required by that customer. It offers key-possession/issuer integration but needs qualified issuance, attestation, trust mapping, termination and rotation. This stage does not build a custom CA or challenge-signature authentication protocol. Reusing a human workspace API key for a production worker is rejected because it conflates client authority with pool/environment/runtime identity and exposes unrelated API routes.

The opaque-credential choice minimizes initial service dependencies. Credentials remain bearer secrets: theft can impersonate the bounded runtime until expiry/revocation. Verified TLS, private local storage, short expiry, current database checks and limited endpoints are required; this is not device attestation or hostile-host isolation.

## Existing integration constraints

- `Environment` already belongs to a project and has local/sandbox/production semantics and an arbitrary configuration field. Preserve those semantics and records; introduce typed immutable connection/execution bindings separately.
- Existing workspace-scoped helpers and foreign keys do not alone enforce same-workspace project/environment isolation. Add complete composite scope constraints and predicates.
- Existing `Principal`, API keys and evaluation `Runner` do not represent a production runtime. Introduce `RuntimePrincipal`; do not grant it a human/service role through generic authentication.
- Executable `RuntimeCommand` already binds installation, epoch, scope, execution/action, worker/generation, intent/decision digests, replay identity and lifetime. It intentionally has no connection/pool/credential-version sidecar. Bind connection selection through the immutable configuration digest already included in the action intent; load current pool/credential authority independently.
- SDK signature, binding and compatibility results do not grant authority. Its synthetic capability profile must not be relabeled as an observation of installed runtime support.
- Schema v12 has a reviewed additive local migration chain. Add the next revision without destructive backfill, production database access, or reuse of the empty-database initializer as an upgrade.
- Backend and SDK declared distribution versions must agree before integration. The separately tracked SDK 0.1/0.2 metadata repair supplies that prerequisite; this specification does not hide it in a new subsystem.

## Records, scope and authority

All customer-owned rows carry workspace/project/environment scope where applicable. Parents gain the necessary composite uniqueness; children use composite foreign keys. API tenancy comes from the authenticated principal and checked parent records, never body claims. Wrong-workspace and wrong-project references have the same bounded not-found response. Use explicit response schemas, not the generic model serializer, for every credential, enrollment, secret and runtime record.

Runtime enrollments, credentials, process sessions and command admissions also bind the installation identity and recovery epoch in which they were issued. Epoch changes invalidate old active/pending credentials and process authority; creating a fresh generation cannot rehabilitate an old credential. Server/database time supplies expiry decisions. A detected clock disagreement beyond 30 seconds places execution authority in a fenced state; this is an operational detection bound, not extra validity for future/expired SDK commands.

| Record | Responsibility and lifecycle |
| --- | --- |
| `Connection` | Stable scoped identity and current active/disabled/revoked state; historical versions remain inspectable. Revocation blocks current use regardless of pinning. |
| `ConnectionVersion` | Immutable canonical typed configuration, connector name/version/artifact digest, allowed operations/destinations, secret-reference IDs/versions, data-handling settings and digest. No mutable latest resolution. |
| `SecretReference` | Scoped opaque resolver/binding/version metadata; no secret bytes or arbitrary caller-supplied file path/cloud resource identifier. |
| `RuntimePool` / policy revision | Scoped pool status, approved connector/platform capabilities, limits and connection allowlist. Revisions are immutable; current disable/revoke remains authoritative. |
| `RuntimeInstance` | Registered pool member, lifecycle, current process generation and bounded liveness observation. A heartbeat is an observation, not proof of correct code or authority to act. |
| `RuntimeEnrollment` | One-use token digest, exact scope/pool/capability ceiling, issuer, expiry, consumed/revoked state. |
| `RuntimeCredential` | Token digest, instance, credential version, active/pending/revoked state, fixed expiry and predecessor/successor relationship. Credential version is distinct from process generation. |
| `RuntimeSession` | One current process incarnation/lease for an instance, an independent session-secret digest, server-assigned generation, expiry and revocation. Public generation metadata alone proves no ownership. |
| `RuntimeCommandAdmission` | Immutable command/digest/recipient/replay identity and durable validation/claim status for integration with the later business outbox. No independent business execution queue. |

Customer owner/admin sessions manage connections, pool policy, enrollment and revocation initially, using existing verification/MFA requirements. Editors/viewers do not gain management authority through an existing generic write scope. Existing API keys do not enroll workers or approve actions. A platform administrator does not implicitly gain customer connection/data authority. Read inventories are bounded, paginated and permission checked. Audit actor, IDs, policy revisions, timestamps and fixed codes; omit tokens, private paths, destination details, inputs and secret values.

Runtime authority is delegated to the registered customer-owned pool, not continuing impersonation of the enrolling person. Removing that person's membership does not silently transfer the runtime to another tenant or change its scope. Workspace/pool administrators can revoke the runtime; workspace suspension immediately denies it. E11 will add more granular governance/delegation without weakening those boundaries.

## Immutable connection and secret contracts

A connection version binds one explicitly installed connector artifact and a nonempty subset of its reviewed operations. Operator-approved connector metadata classifies effects and destination requirements; a method named read is not inherently harmless. Model output or package text cannot add an operation, substitute a base URL, choose an executable or register a connector. E03 supplies a fixed synthetic connector for verification, not a marketplace/plugin loader.

Use a versioned connection-configuration schema, strict typed JSON, the existing reviewed JCS library and a domain-separated SHA256 content identity. Bound the complete decoded configuration and nested fields before canonicalization; unknown schema/connector policy forms are rejected. The implementation plan must freeze canonical fixtures and bounds. A configuration digest identifies admitted content; it never proves publisher trust or permission to connect.

The later immutable deployment configuration maps package connector/credential declaration IDs to exact connection and secret-reference versions. Its canonical digest participates in the existing action binding. Current revocation is checked separately: old configuration remains reproducible but cannot override a disabled connection, revoked grant, old worker generation or recovery fence. No new unsigned transport field grants connection permission.

Destination policy specifies normalized HTTPS host/port and the connector's bounded path/resource rules. Refuse URL credentials, fragments, redirects, arbitrary proxies, unrecognized policy forms and request-selected origins. Apply the policy at actual connection establishment, pinning the validated address while preserving TLS hostname/SNI verification. Test DNS rebinding, IPv4/IPv6, encoded path escapes and redirects against real local fixtures. Deny metadata/link-local and installation control-plane/secret-service destinations. Explicit operator-approved private network ranges can be allowed for customer systems; private addresses are not broadly trusted. Pool egress enforcement complements the application transport checks. Unsupported transports fail closed rather than silently bypassing this path.

Secret resolution occurs only inside the isolated worker execution boundary after identity, current authority, connection and destination checks. The API, engine, package, model context, command and audit never receive secret bytes. Resolve only the reference required by that connector, pass it only to that connector invocation, and keep fleet credentials and other connections' secrets out of its environment. Bound reads, lifetimes and responses; do not promise reliable memory zeroization in Python.

The first concrete resolver is an operator-provisioned private mounted-secret mapping: opaque binding IDs map to explicit versioned files under a configured root. Refuse symlinks/escape, unsafe ownership/permissions, wrong versions, oversized values and changes detected during an opened read. Registration cannot supply a path. Operator custody and immutable version management are part of this provider's contract; it does not prove tamper resistance against the host administrator. A missing/unavailable resolver denies use. Fixture data tests this provider; Vault/cloud/dynamic-secret integrations retain separate qualification.

Secret rotation creates a new reference/version and connection configuration; it does not silently change an approved principal or credential version. Later re-admission/approval rules determine whether an action must be reproposed. E03 records provider version metadata only, never a public digest of low-entropy secret bytes. No custom encryption/key vault is introduced.

## Enrollment, transport and credential rotation

Production runtime transport uses direct verified HTTPS with an independently provisioned API origin and CA trust, bounded requests/responses/timeouts, no ambient proxy and no redirects. Loopback HTTP is allowed only in explicitly isolated development/test mode. Never trust caller-supplied certificate-forwarding headers. The `authenticate_runtime` boundary can later map an established workload identity to the same current records without changing business permissions.

Tokens contain at least 256 random bits and have a distinct runtime/enrollment prefix so generic human/API-key routes reject them. Store only token digests on the server. Deliver bootstrap material once through an authenticated no-store response/private file; CLI accepts protected stdin/file, never URL or process arguments, and writes owner-only files without printing the secret. Treat missing/unsafe storage as an error.

Enrollment defaults to ten minutes and one successful consumption. The exchange transaction locks the enrollment, checks expiry/revocation and all parent status/policy, creates the runtime/credential, and consumes the token atomically. Registration fields cannot widen the server-defined scope. Concurrent consumers yield one winner. Lost initial enrollment response requires explicit revoke/reissue; the one-use token is not made reusable to recover a lost secret.

Active credentials have a fixed fifteen-minute lifetime; workers begin rotation with at least five minutes remaining and bounded jitter. There is no indefinite static refresh credential. The normal network-loss path uses two-phase rotation:

1. **Prepare:** active credential C and the current process-session secret authenticate; lock the instance, current session and credential. Create one pending successor P with a 60-second activation deadline, the same bounded scope and that session/generation binding. Return P once; store its digest only. C keeps its original expiry. A retry creates a replacement pending P and invalidates the unactivated predecessor; it never extends C.
2. **Persist:** the worker atomically stores both C and P in private durable state before activation. Serialize rotation locally and reject late responses from older prepare attempts.
3. **Activate:** pending P may only call activation (no polling, heartbeat, command claim or renewal). P plus the current process-session secret authenticates this path; the server loads predecessor C rather than requiring its revoked-or-soon-to-be-revoked bytes in the request. Under the same lock, require P current/unexpired, C still active/unexpired, unchanged registration/policy and P's still-current session/generation. Activate P with a fixed fifteen-minute expiry, revoke C and clear that pending relationship atomically.
4. **Resolve response loss:** retry activation with durably stored P. If already active and current, return its original expiry and safe self-state without extending it. This separate metadata-only path requires P and current scope/epoch checks, but neither predecessor C nor a surviving process session; it grants no session authority and must preserve any subsequently prepared successor Q. If P was replaced/expired/revoked, deny; if C remains valid, the worker can prepare again after obtaining current session authority.

Pending cancellation requires the authenticated current predecessor and current process-session secret, and only affects its still-pending successor. It cannot revoke an activated successor after a race. Prepare/activate/cancel/revoke serialize on the same instance lock; current scope/recovery fences are checked on each. Expired predecessor activation is refused. A process outage beyond all credential expiries or loss of all persisted secrets requires new enrollment; that bounded recovery behavior is documented, not a hidden perpetual credential.

Use a one-minute process lease with a twenty-second heartbeat as initial engineering defaults. Only one active process session owns an instance. A restart may reclaim after expiry; an administrator can revoke immediately. Server-assigned takeover increments the fencing generation and invalidates old session claims; it does not preempt an unexpired healthy session merely because another caller presents a copied credential. Routine credential rotation preserves the generation. Cloned bearer material is not device identity; compromise requires revocation and re-enrollment. Waiting business executions later live in the engine and do not require an occupied worker process.

Acquisition returns a separate random 256-bit session secret once, stored only as a digest by the server and held in the supervisor's private memory. Do not return it from inventory/self-state, persist it with the reusable instance credentials, log it, or pass it to connectors. Heartbeat, polling, command claim, rotation prepare and pending-P activation require both the appropriate credential and this current session secret; public session IDs/generations are insufficient. Every operation checks the lease is still unexpired under the same instance/session lock. A late heartbeat cannot resurrect an expired lease. Lost acquisition response leaves that lease occupied until its bounded expiry; it cannot be replayed from digest-only storage or preempted using C alone.

Takeover after expiry increments generation and invalidates old-session pending successors. After a crash the worker keeps persisted C/P until it identifies the active credential using safe authentication/self-state or active-P activation replay, then acquires a new process session after the previous lease expires. Pending P cannot recover a lost session secret or activate under a new generation. Routine successful credential rotation keeps the session secret but requires the new active credential for later operations. This prevents a copy of the instance credential alone from posing as the current process; possession of both credential and live process memory remains a compromised trusted host, not something this scheme attests against.

## Command integrity, replay and dispatch boundary

Use the existing SDK command framing, full validators, Ed25519 implementation and exact binding checks. Command public-key trust is provisioned independently; a key ID inside an envelope never supplies trust. Publisher keys and runtime command keys have separate custody. Workers receive verification keys only. Operator-managed signing keys are loaded privately through configured custody; no public arbitrary-command signing endpoint exists.

Persist exact canonical command bytes/digest and recipient scope/generation before delivery. Uniquely constrain replay identity by installation/epoch/workspace and check command-ID conflicts separately. Same identity/same digest returns the prior status; changed content conflicts. Invalid signature, wrong context, expiry, missing or stale authority, current connection/pool revocation and epoch/generation mismatch refuse admission. Replay checks are durable across server/worker restart. Keep terminal tombstones for at least 24 hours and beyond command expiry plus the permitted clock skew; retain in-progress/uncertain records until explicit reconciliation/retention policy permits deletion. Clock skew tolerance never widens the SDK's five-minute command lifetime.

Authenticate and scope every request before consulting or returning a prior replay result. A duplicate cannot use historical success to bypass present revocation or obtain another tenant's status. Persisted in-progress/uncertain claims are not reusable permission to perform an effect again.

Build binding context from authoritative pinned records, not a context supplied by the worker or command sender. Verify the actual input/target/configuration and connector artifact against those records. Installed capabilities are observations intersected with the current pool policy and work requirements; self-report cannot increase permission.

`BusinessDispatchAuthority.authorize(current_identity, command_digest, pinned_records)` is a required internal dependency. Its absent/default production implementation denies. E03 exposes no public effectful business dispatch, model/tool execution or arbitrary command submission. It tests signature/replay/claim behavior with a clearly isolated no-effect fixture sink that cannot be configured in production. Secret resolution is exercised with fixture authority only in test mode. E04/E05 must supply persisted deployment/execution/action/decision state and the transactional pre-effect claim; E08 supplies applicable entitlement/admission rules. E03 does not manufacture fake production records to make the foundation look complete.

The delivery interface accepts an existing database transaction so the later business outbox can commit intent and delivery together. E04 owns the command outbox/event inbox and business execution state; E03 does not create a competing queue or repurpose evaluation jobs. Authenticated event sources, event sequence validation and projections remain that next integration's responsibility.

Disconnection, authority/database unavailability, stale trust state and revocation block new consequential dispatch. A previously sent external request cannot be recalled by changing a database flag. Generation fencing prevents new claims and stale Lotuspond commits; uncertain remote outcomes require E05 reconciliation. No lease, signature or database uniqueness constraint is advertised as exactly-once external execution.

## Recovery authority and signing-key lifecycle

Define `RecoveryAuthority.current(installation)` to return independently established epoch and active/fenced status. Missing, unavailable or mismatched authority denies generation activation, renewal into active execution authority and dispatch. An epoch column or file restored with the application database cannot establish current authority or detect an undeclared rollback.

E03 implements the fail-closed integration boundary, independent local fixture and an operator runbook contract. Production recovery activation requires a separate current authority/custodian procedure, invalidated prior credentials/generations, current grant/identity revalidation and downstream reconciliation before writes. A fresh epoch alone does not recover post-backup revocations. A controlled restore must fence before API/worker restart; an automated rollback witness or externally controlled monotonic authority needs its own qualified integration. No always-allow production fixture is shipped. E04/E05/E09 retain real restore/reconciliation and custody qualification.

Command signing-key rotation provisions the new public trust revision before issuance, retains verification availability only for the explicitly allowed transition interval, and refuses revoked keys for new dispatch. Authority availability is required even if a cryptographic signature verifies locally. Changing publisher or command trust never silently changes the other. Tests cover old/new/revoked keys and lost trust distribution. External KMS/HSM integration and distribution signing remain separately qualified; this design uses existing cryptographic primitives and private key loading, not a new key-management service.

## API, client and implementation boundaries

Add scoped management resources under `/api/v1`: connection identities/versions/secret-reference metadata, runtime pools/policy revisions, enrollments and instance inventory/revocation. Add a separate runtime route group for enrollment exchange, credential prepare/activation, session acquisition/heartbeat and self-state. Runtime tokens authenticate only that group. Enrollment tokens authenticate only exchange; pending tokens authenticate only activation. Validate bounded identifiers and strict JSON; reject unknown fields and oversized input. Rate-limit unauthenticated exchange, authenticated rotation and polling separately.

Mutation idempotency keys bind the full scope and canonical request digest for non-secret-returning management operations. Same key/same request returns the existing result; changed request conflicts. Secret issuance uses the explicitly described one-time/rotation protocols rather than claiming replayable secret responses from digest-only storage. List/health responses expose safe status and last-observed timestamps, never credential digests, secrets or false healthy metrics.

Expected implementation ownership: additive backend fleet/connection modules and strict schemas; a separate runtime Python package/client/supervisor/transport/resolver; minimal API wiring; migrations and concurrency fixtures; SDK consumer tests without changing pure contracts; operator/SDK docs and API changelog. No UI work, engine dependency, arbitrary-code loader, live secret-store connection or production deployment is included in this plan boundary. Existing execution-distribution/evaluation clients continue unchanged.

Actual compiled-package deployment, business admission, agent/model/tool execution, human decisions, licensed capacity, remote-provider effects/outcomes and customer-facing authoring/operations remain the approved next workstreams. Each must integrate these controls before its own completion claim.

## Assumptions and owner decisions

The connected isolated Linux topology and initial owner/admin management follow the approved master design. Token/lease durations, transaction strategy, strict errors and package boundaries are engineering defaults subject to evidence and review; they do not choose a customer market or remove a feature.

Before external qualification, the owner/customer must identify the first workflow and supported systems, permitted actions and autonomy/review roles, builder experience, installation/data/model placement, actual secret store/workload issuer, recovery/key/backup custodians, infrastructure scope, capacity/license/grace terms and support ownership. If a first buyer mandates mTLS, offline operation or a specific secret store, its qualification moves onto the critical path. Those questions do not block this written foundation design or justify silently changing the product scope.

Written-spec approval is the next gate. After approval, produce a detailed implementation plan with the already selected subagent execution/review method; obtain plan review before implementation. No production access, outbound communication to customers, cloud change or additional PR merge is authorized by approving this design.
