# Proving a workflow package before release

Date: 15 November 2026 (Asia/Kolkata). Status: **design, decided by Claude under the owner's delegation ("proceed to build in the order"); this change builds it.** It serves the Prove row of [GOAL.md](../../GOAL.md) ("evaluating a workflow package version itself, not only an agent behind HTTP; the provider that binds a package version to its release decision at deployment"), milestone 5 of [invoice exception triage](2026-11-11-reference-workflow-design.md) and milestone 4 of [late purchase order recovery](2026-11-14-late-purchase-order-design.md).

## What exists

- Scenarios, evaluation runs, release policies, releases, independent approval and release decisions, for agents behind HTTP. A decision's evidence is canonical JSON with a SHA-256 digest.
- Deployment admission already accepts a `release_id` and re-verifies the whole release pipeline in its own transaction (`validated_release_binding`): the policy verdict recomputed, approvals by a second administrator, the stored decision's evidence equal to the recomputed one. It first asks an assurance provider for the evidence that ties the release to the package version. **No production provider exists**, so every release is refused and production can only deploy with `release_required` switched off.
- A package may declare evaluations (`assurance.evaluation_refs`); declaring any makes a release required at deployment.

## Decisions

1. **A package evaluation run is an ordinary evaluation run** whose subject is a package version: its `revision` is `package:<publication sha256>@<deployment revision>`, the subject and the evaluation deployment it ran on. Its scenarios are the project scenarios the request names; each one's `input` is the package input and its `expected` describes the outcome (below). No new scenario kind or column: an ordinary scenario is a package scenario by being named in a package evaluation. The release policy, decision, approval, gate and evidence export work on it unchanged.
2. **It runs the real package** on the durable engine, through an evaluation deployment of that publication in the same environment as the production deployment, bound to evaluation connections (stand-ins or test systems) rather than production ones. One execution per scenario, started with an idempotent request key, so the run finds each execution again without new storage. A run in another environment is not possible today: a deployment's stored release link (`deployment_assurance_bindings`) has a foreign key to the candidate run that includes the environment, so a separate evaluation environment needs a reviewed migration (later work).
3. **What is observed.** A scenario's outcome is the execution's terminal state and result, or, when it stops at a person's review, the exact proposed action (operator, target and input). **Extended 2026-11-18:** an execution that stops at a person's form is observed as `{"state": "form"}` and cancelled; the form is never submitted. Before this, a scenario ending at a form never completed its run. An evaluation never approves an action: at a review the observation is recorded and the execution is cancelled, so evaluating a package writes nothing to a system. Agent proposals, routing and results are what a release proves; writes are proven by read-back and verification at run time.
4. **Pass.** `expected` is `{"state": ..., "result": {...}, "proposal": {...}}`, each part optional; a scenario passes when every value it names equals the observed one (objects match as subsets). An execution still running when the run's deadline passes is a failed, inconclusive scenario.
5. **Advance on request, one gated step at a time.** The run advances when its owner asks (`POST …/package-evaluations/{run_id}/advance`), repeatedly until it is `completed`. Each call admits one scenario not yet started, or else cancels one execution at its review after recording the proposal, or else records every finished execution. Admission and control take the fair gates before any row lock, so a transaction may take only one such step. No new worker.
6. **The release binding provider** (`ReleaseEvidence`) answers with the evidence when the release's candidate run is a completed package evaluation run of exactly that publication and the release has a passing stored decision. The evidence expires 7 days after the decision. Admission then re-verifies everything as today. The deployment's configuration (its own connections) is not part of what an evaluation proves; it is checked by admission as for every deployment.
7. **Composed everywhere.** The API, workers and harness all get the provider, so `release_required` (on by default in operator mode) can stay on. **Corrected 2026-11-17:** it could not. With `release_required` on, the evaluation deployment itself was refused, so nothing could be proven and released; the conformance case passed only with the gate off. [Evaluation deployments](2026-11-17-evaluation-deployments-design.md) repair it: a deployment whose configuration says `"purpose": "evaluation"` is admitted without a release, only a package evaluation starts it, and it never writes.

## Out of scope

A scheduler for evaluations, cost reporting for package runs (cost is reported as zero, known, because model usage is accounted per execution), baseline selection rules beyond what releases already have, and the console pages for evaluations (Control Room work).
