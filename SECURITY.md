# Lotuspond security boundaries

- Authenticate before accessing workspace data. Verify human membership or key scopes on every request and include workspace predicates in every query.
- Use composite workspace foreign keys to reject cross-workspace references. Never rely on opaque identifiers as authorization.
- Hash passwords with a random salt and a memory-hard derivation. Store only session and API-key hashes. Keys expire, are scoped, and can be revoked.
- Browser sessions are HttpOnly and SameSite=Strict. Mutating session requests require a permitted Origin. Production cookies are Secure.
- Authenticator-enabled accounts cannot receive a session from password verification alone. Use bounded expiring login challenges, transactionally consume codes, reject reused TOTP counters, and bind verified sessions to the current user/factor/version. Initial enrollment requires the current password and code confirmation; factor changes require the password and a fresh enrolled factor or recovery code. Production platform operators must use MFA and cannot disable it. An operator may require an authenticator for every workspace on the installation through configuration, which needs the encryption key and is refused without it. An organization may additionally require one for its own access; only an owner or administrator who already holds an enabled factor can set or withdraw that requirement, it never applies to a personal workspace, and while it is on both member sessions and the keys created by those members are refused with `mfa_required` until the person enrolls. Withdrawing it restores the previous access; it deletes no factor, key or membership.
- Encrypt authenticator secrets with a dedicated stable operator-managed key and user/factor-bound associated data. Store recovery/challenge digests only. Show recovery codes once, keep them out of logs/cache/browser storage, and revoke prior sessions when authentication material changes. Password-reset links do not remove MFA. Missing configuration never permits a password-only downgrade. Factor key rotation and assisted lost-factor recovery need a separate reviewed design.
- Users can inspect and revoke only their own sessions. Password changes require the current password, revoke all previous sessions, and rotate the current cookie in one transaction. Serialize sign-in and password changes on the user row to prevent old-password session creation after rotation. Never return session token hashes in session inventories.
- Notify the account mailbox out of band whenever authentication material changes: password change, password reset, authenticator enrolment, authenticator removal and recovery-code reissue. The notice states what changed and when and carries no link, token or code, so it cannot be repurposed for phishing and needs no expiry. A disabled or unconfigured mailbox never blocks the security change itself.
- Mailbox challenges and invitations are expiring and single-use. Store token hashes; encrypt queued message bodies using an operator-managed key. Reset requests use a generic acknowledgement, and reset completion revokes all sessions without signing the account in automatically.
- Generate identity links only from the configured public origin. Keep tokens out of API responses, audit records, logs, and browser history. Organization invitations require a matching verified mailbox and cannot silently change an existing member's role.
- SMTP is an operator-controlled destination and requires verified TLS in production. Mail submission uses a separate worker with expiring claims and bounded retries. Bound the whole SMTP conversation, not only each socket operation; a conversation that passes its bound releases the worker and stays retryable. Queue acceptance, SMTP acceptance, and inbox delivery are distinct states.
- Offline enrollment records a separate operator attestation and never sets mailbox verification. Pending users cannot authenticate. Store only token digests; write enrollment links exclusively to private files, consume them once, revoke prior sessions and attributed keys, and require normal login afterward. Serialize completion and reissue on the user row. Production organization/operator authority requires a verified mailbox or an active attestation linked to completed enrollment; email invitations still require verified mailbox ownership.
- Email recovery for an offline-origin account requires completed enrollment and actual mailbox verification, including after an installation changes network mode. Recheck eligibility when consuming a reset challenge. A claimed email address must never inherit operator-attested authority through password recovery.
- Keep release approvals independent: requesters cannot approve their own requests, API keys cannot approve, and a decision cannot be overwritten.
- Mutating API requests carry `application/json`, which a cross-site form cannot submit. There is no exception since OTLP protobuf ingestion was retired (ADR-0013).
- Validate untrusted request shapes and bounds. Keep SQL parameterized and table/column names selected only from static server definitions.
- Workflow-package validation is a local declaration check, not permission to execute. Accept only the supported version and node kinds, bounded input and graph shapes, declared references, and explicit agent limits. Reject unknown fields, duplicate JSON keys, nonfinite numbers, and invalid graphs. Connector credentials are secret references; instructions and other free text still require author review for sensitive content. A content digest supplies integrity identity, not publisher trust, approval, tenant authority, or runtime capability. Package validation does not resolve references, load plugins, call models, or perform business actions.
- Registry admission uses the complete package validator and preserves exact canonical bytes without evidence redaction. Workspace/project predicates and composite foreign keys bind immutable versions and request-key results to the authenticated tenant. Publication conveys no execution or release authority. Lists and audits contain fixed identifiers and digests, never manifest free text. Stored validator/canonicalization identifiers describe admission semantics only.
- Outbound model destinations are operator configuration, never arbitrary request URLs. Require HTTPS, reject URL credentials, refuse redirects, and bound time and response size.
- Do not log credentials, session cookies, prompts, or raw response bodies. Redact sensitive evidence keys: any key naming a password, secret, authorization, cookie, API key or token. The one carve-out is a usage count — a key ending in `tokens` whose value is a non-negative integer, such as `gen_ai.usage.input_tokens` — which is evidence rather than a credential; a key that also names a credential stays redacted. Producers must remove personal and confidential content from free-text evidence before submission.
- Public errors must not expose provider responses, connection strings, database exceptions, or stack traces.
- Worker execution occurs in a separately managed process. The API does not execute arbitrary uploaded code.
- Customer-side runners execute only operator-selected adapters in bounded subprocesses. Keep control-plane keys and lease tokens out of adapter environments and payloads; renew leases independently, stop on lost authority, and submit only complete evidence after process cleanup. Process groups do not contain hostile code or prove external-resource teardown. Unconfirmed cleanup must stop further execution. Packaged HTTP, MCP and A2A commands must not receive a Docker socket. `LOTUSPOND_API_URL` may be an origin or the `/api/v1` base. The API client uses direct transports, ignore ambient proxies, and keep TLS verification enabled.
- An organization owner or administrator may clear a member's authenticator when that member lost every factor. It must be a different person, it requires the administrator's own password, it never touches a platform operator's factor, and it only removes: no session, factor or password is issued, so it cannot be used to take over the account. The member is notified out of band and re-enrols themselves.
- A process group bounds an adapter's lifetime and resources, not its privilege. The supervised runner executes the operator's own code on the operator's own host; code Lotuspond supplies runs in a container with no network instead. `LOTUSPOND_ADAPTER_ROOT` optionally confines which directory may supply an adapter, resolving symlinks first. Never promote a process group into the isolation boundary for hosted multi-tenant execution.
- Enforce budgets transactionally. Missing provider configuration, incomplete evidence, and missing authorization must fail closed.
- Local trust-authenticated PostgreSQL is a development convenience only. Production requires reviewed database roles, TLS, retention, backups, distributed quotas, verified identity flows, monitoring, and operational validation.
- Never infer readiness from a green build. Document unresolved integration and operational work in `docs/CAPABILITIES.md`.

Session lifecycle review reference: [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) and [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), checked 2026-09-21. These inform the controls above; local tests do not certify compliance.
